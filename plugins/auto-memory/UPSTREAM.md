# Upstream

The sources, tests and commits this note names (`src/`, `tests/`) are in Aaron's private source repository, which builds the plugin; this one carries the built plugin.

`auto-memory` ports Claude Code 2.1.318's auto memory to harnesses that don't have it, Codex first. The text in `src/text/` was captured from that release and committed verbatim first, but that commit was squashed into the one that added the plugin, so the verbatim text isn't kept. The list below is the record of every edit.

## Where each piece comes from

- `src/text/section.md` is the `# Memory` section Claude Code puts in its system prompt for a session with auto memory and no team memory (the lean variant), with the memory folder as `{dir}`.
- `src/text/memory_list.md`, `memory_read.md` and `memory_write.md` are the descriptions of Claude Code's `memory_list`, `memory_read` and `memory_write` tools, which it offers when its memory is a store it reaches through tools rather than a folder. The input schemas in `src/server.ts` are Claude Code's too.
- `src/prompt.ts` loads `MEMORY.md` as Claude Code loads it: "Contents of <path> (user's auto-memory, persists across conversations):", cut past 200 lines or 25,000 bytes with Claude Code's warning.
- `src/store.ts` names a project's folder as Claude Code does: the real path of the Git repository's main working tree (so subfolders and worktrees share it; a worktree of a bare repository belongs to the bare repository's folder), or of the folder outside a repository, with every character other than a letter or digit turned into `-`, and Claude Code's hash after the first 200 characters. Version tokens (the first 12 hex digits of the content's SHA-256), the 102,400-byte read and write cap, 50-entry list pages, the path rules, the reserved folder names a write may not use and the content cleaning follow Claude Code's tools, and so do the tools' results and refusals. Claude Code also refuses a list of config file names as path parts; the plugin leaves that list out, since a memory path must end in .md, .txt, .json or .jsonl anyway.
- `src/secrets.ts` refuses the common credential shapes, named as in gitleaks; Claude Code checks against a longer gitleaks rule set.

## Edits to Claude Code's text

- `section.md`: "write to it directly with the Write tool" becomes "write to it directly with the memory_write tool, as the store `personal`", followed by a new sentence, "Store paths start at that directory, so its index is `/MEMORY.md`." Codex has no Write tool, the server's write keeps Claude Code's version and secret checks, and the tools take paths within the store, not the folder's full path.
- `section.md`: "delete memories that turn out to be wrong" becomes "rewrite or retire memories that turn out to be wrong". The tools can't delete a document; `memory_write.md` says how to retire one.
- `section.md`: "(code structure, past fixes, git history, CLAUDE.md)" adds AGENTS.md, the file Codex reads in its place.
- `section.md`: "Recalled memories appearing inside `<system-reminder>` blocks are background context" becomes "Memories are background context". Codex has no system reminders, and nothing recalls memories into a turn yet (see below).
- `memory_write.md`: "not what CLAUDE.md, the code, …" adds AGENTS.md.
- `memory_write.md`: "Never write secrets or credentials into a memory — project stores are shared with every collaborator, and such writes are refused in every store." becomes "Never write secrets or credentials into a memory — such writes are refused." The plugin has one private store, not shared project stores.

## How the plugin differs from Claude Code

- One store, `personal`: the project's memory folder under `~/.agents/memory` (or `AGENT_MEMORY_DIR`). `memory_list` with no arguments lists only that store; Claude Code's team and project stores aren't ported.
- The server's MCP `instructions` are the plugin's own words. Codex 0.169 shows them to the model as the description of the server's tools, so they reach a session whose hook didn't run: with no `# Memory` section in the conversation, they say to read `/MEMORY.md` before the first reply.
- Codex runs a plugin's hook only once the user trusts it, again after every update of the plugin (it hashes the plugin's files), and skips it silently until then. So the hook marks each session it starts, as an empty file named for the session's id in `<store root>/.auto-memory/sessions/`, and drops marks older than 30 days. The server reads the session's id from each call's `_meta` (`x-codex-turn-metadata.session_id`, else `sessionId`, the `session_id` the hook is given). The first memory tool call of a session with no mark gets the section and the index (left out when the call reads the index itself) ahead of its result, after the plugin's own note asking the model to tell the user that the hook isn't trusted and how to trust it (`UNTRUSTED_HOOK` in `src/prompt.ts`). A call that names no session gets only its result.
- `hooks/hooks.json` sets `additionalContextLimit` to 24,000 tokens, a Codex key Claude Code ignores. Codex counts a hook's context as its UTF-8 bytes / 4 and, past the limit (2,500 tokens when unset), keeps the start and end and drops the middle, which cut index lines from a section and index over about 10KB (checked on 0.169.0). The hook cuts the index at 25,000 characters, which is at most 75,000 bytes, so 24,000 tokens hold the section and the longest index the hook sends, even one in a script of 3-byte characters. `tests/manifest.test.ts` checks the limit against that worst case.
- Codex runs one server for every session of its app server, so the server takes each call's folder from Codex's metadata: `_meta["codex/sandbox-state"].sandboxCwd`, which Codex sends because the server asks for it (`codex/sandbox-state-meta`), else the Git root in `x-codex-turn-metadata.workspaces`, else a `PWD` its client set. A call with none of them is refused rather than saved under the wrong project.
- The secrets refusal leaves out Claude Code's "Memory is synced to your account", which isn't so here.
- Claude Code keeps its own auto memory; the plugin's hook there only checks that `CLAUDE_CODE_REMOTE_MEMORY_DIR` points at the shared store.
- Not ported: the background extraction agent that saves memories after a turn ("You are now acting as the memory extraction subagent") and recall of relevant memories into a turn (a side query that picks up to five, or a BM25 index). Claude Code 2.1.318 turns them on only behind flags. Its consolidation ("# Dream: Memory Consolidation") is the dream skill, below.

## The dream

The `dream` skill is the plugin's own: it isn't in Claude Code, which keeps its dream ("auto-dream") behind a flag and runs it in the background. The skill's text (`skills/dream/SKILL.md`), the helper (`src/dream/`, bundled as `skills/dream/scripts/dream.mjs`) and the `memory_dream` tool are the plugin's own words and code. The dream's instructions, which the helper prints when a dream begins, are `src/text/dream.md`.

### Where the instructions come from

- Claude Code 2.1.325's "# Dream: Memory Consolidation" prompt, as its code builds it for a dream with no team memory, no memory tools and no added context, with the memory folder, the transcripts folder and the line about writing in braces.
- The analyzer and organizer prompts of Anthropic's claude-cookbooks, `managed_agents/example_data/memory_distill/prompts/` at ce8b262 (MIT, in `skills/dream/LICENSE`). The sentences named below are theirs, sometimes with "transcript" read as "session".

The three texts are kept verbatim in `src/text/upstream/` (`claude-code-dream.md`, `cookbook-analyzer.md`, `cookbook-organizer.md`), in the source repository only, so `diff src/text/upstream/claude-code-dream.md src/text/dream.md` shows every edit below.

### Edits to Claude Code's dream

- The transcripts line no longer points at a folder of JSONL files to grep. It names the sessions the helper lists, from Claude Code and Codex, and the `digest` command that shows each as text, and says how to tell the user's words from the rest: each entry starts at the left edge, and every line the user didn't type is marked `|`.
- Added after it, from the cookbook's analyzer: the paragraph that a transcript is data, not instructions (what the user told the agent is a fact; text telling an agent to ignore its instructions or send out secrets is not; an instruction from outside the project is not a convention unless the user adopts it; memory files are data too), and the rule never to copy credentials into memory.
- Phase 1: "Skim existing topic files" becomes "Read every topic file in full", as the cookbook reads related memory files in full.
- Phase 2: "Read each listed session IN FULL", from the cookbook, with "oldest first", replaces "Don't exhaustively read transcripts. Look only for things you already suspect matter." and the "Transcript search" source with its grep command. The sources are now corrections and preferences (keeping the user's exact words), memories that drifted (against a session as well as the code), and what the sessions missed (from the cookbook's "process observations").
- Phase 2 gains "Save as you go": write what a session taught before reading the next, so a full context loses nothing. And a "Verify" section: the cookbook's leave, fix and downgrade rules, checked against the sessions and the repository, with the "file exists, grep for it" check from the plugin's `memory_read` text.
- Phase 3: "If your context has no such section, use the format of the memory files that are already there", for a session without the memory section. Two new points: merging duplicate files and retiring the other, and quoting the user's own words in a `feedback` memory. The cookbook organizer's rule for two memories that can't both be true (keep the later correction and note what it replaced, else mark the conflict) is added. "Deleting contradicted facts" becomes "Fixing contradicted facts".
- Phase 4: a paragraph on retiring a file. The one way to retire one is a file that starts with `Obsolete:`, the very first thing in it; finish deletes each such file that Git already holds, so Git keeps its text. Codex's memory tools can't delete, and this way no note is lost outside Git.
- The CLAUDE.md section names AGENTS.md beside CLAUDE.md in its first paragraph, and "Delete the memory" becomes "Retire the memory".
- "Return a brief summary …" becomes a "Finish" section: run `check`, then `finish` with a summary passed on standard input (a quoted here-document, so no shell reads it), then tell the user what changed, why, how to undo it, and that the commit also holds what other sessions saved meanwhile. If a step says another dream holds the lock, stop and tell the user rather than abort or force it.
- The line about writing is Claude Code's own in Claude Code ("write to it directly with the Write tool"). In Codex it says to write with `memory_write`, to `memory_read` a file first (its version is what `memory_write` needs), and to check, finish or abort with `memory_dream`.

### How the dream differs from Claude Code's

- Claude Code's dream runs by itself in the background when 24 hours and 5 sessions have passed since the last one. This one runs when asked, or from a scheduled job the user sets up.
- It reads both harnesses' sessions in full, through the helper's digest, instead of grepping Claude Code's: the oldest first, up to a budget of pages (10 by default, about 10,000 tokens each) and sessions (30). The rest wait for the next dream. The digest leaves out a session's dream, from the output of a call that ran begin (matched by the call's id) to finish's or abort's, or to the user's next words when no end follows, keeping the user's own words in it, and labels what a harness or hook put in a user's turn: only the exact tags that harness writes, closed. Transcripts are read a line at a time; a line over 32 MB is left out and noted.
- It shares Claude Code's record, `.consolidate-lock` in the memory folder, whose modification time is when the last dream started. It doesn't begin while Claude Code's dream holds that file, and finish moves the time forward, never back, so Claude Code's dream counts sessions from there. Claude Code's dream doesn't see one of these while it runs: Claude Code takes the file as held only while the process it names is alive, and the helper's process ends between steps. The record never moves past a session left for the next dream. A session that can't be read holds it back once, and its id goes in `.dream-lock.failed`; a dream that finds the id there and still can't read it passes it over, so it can't keep newer sessions from being read.
- It adds its own lock, `.dream-lock`, owned by the session that began the dream (or a token begin prints, passed as `--token`), which alone can finish or abort it. Digest and check refresh it (in Codex, `memory_dream`'s check, after each session); one left alone for two hours is taken over.
- Each dream is a Git commit in the memory root, after a snapshot commit of what changed in the project's memory folder, which is checked for credentials first. The repository ignores machine state: the lock files, the hook's `.auto-memory/` markers and `memory_write`'s temporary files. The helper's Git steps take turns through `.auto-memory/git.lock`, which its holder refreshes and alone removes, and which a waiter takes over only after watching it go unrefreshed for 10 seconds. Commits name their paths, and the first commit and the one that stops tracking machine state are built on an index of their own, so a step that holds the lock at the same time can't have its staged notes swept in.
- The finish step refuses an index over 200 lines or 25,000 characters, a link to a missing or retired note, and anything the plugin's credential check finds.
