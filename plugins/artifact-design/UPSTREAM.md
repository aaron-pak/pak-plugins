# Where this plugin comes from

The sources, tests and commits this note names (`src/`, `tests/`) are in Aaron's private source repository, which builds the plugin; this one carries the built plugin.

The plugin began as a copy of Claude Code's own artifact skills, with an MCP server that stood in for Claude Code's Artifact tool, and it was kept word for word in step with Claude Code up to 2.1.304 (2026-10-19). Since 2026-11-10 it goes its own way. It is built around a design system, each feature is kept for what a page needs and not for parity, and nothing in it is re-synced with Claude Code any more. This note says what is still Anthropic's text and what the plugin does on its own.

## Still Anthropic's

- `artifact-diagramming` is Claude Code's skill verbatim (2.1.304), less one sentence on how an artifact made from an Artifact type draws diagrams.
- `dataviz` is verbatim, with its `references/` and `scripts/` unchanged, in `codex-skills/`, which only Codex's manifest names: Claude Code lists its built-in `dataviz` in every session, so a second copy would only repeat it. It leaves out one sentence of its description on handing chart rows to a first-party document connector.
- `skills/artifact-design/design.md` is the design guidance of Claude Code's `artifact-design` skill (2.1.304): Read the request first, the fundamentals, the design plan and the editorial process. It is for a page that uses no design system: `quickstart` returns it where none is installed, and `guide` returns it as the part `General design` where one is. It leaves out what the page rules now say (the title, the check before publishing, a page complete at rest) and everything about Markdown, and adds the theme tokens' shape and a line on Mermaid, which the page contract used to carry.
- The publish skeleton and its content security policy, the Mermaid runtime (Mermaid 11.16.1, loaded from jsDelivr), how a page's name and description are read, and the general checks and report of `ArtifactCheck`'s preview were ported from Claude Code 2.1.300 and still follow it, with one change to the Mermaid runtime: it waits for the page's font before it draws, and draws again when a font arrives later. Mermaid sizes each label's box from the font it finds, so a diagram drawn before a web font loaded had its labels cut off once the font came in.

Model-facing text names no tool, type or service the plugin doesn't have, and a test checks the tool listings, the skills and the guidance for those names.

## The plugin's own

**One short tool.** The `Artifact` tool's description says when to use it and that `quickstart` comes first, and nothing else; it is the same for Claude Code and Codex, and fits Claude Code's cut at 4,096 characters (2,048 before 2.1.296) and Codex's 5,000-byte limit on an input schema. The tool asks Claude Code to load it up front (`anthropic/alwaysLoad`), and the Codex manifest does the same with `omit_tools_from`. In earlier runs the skill alone, without a tool in sight, got its answer in chat instead of a page 3 times out of 3. The description names what gets a page without being asked (an explanation, a walkthrough, a comparison, anything that takes a diagram) and says a terminal can't draw: asked on 2026-11-11 to explain a script where "a diagram would help", Opus drew the diagram in terminal text 3 times out of 3 with the description before it, and made a page 6 times out of 6 with this one, while seven questions with a short answer (a fact twice, an edit, a verdict, a how-to, a why, a fix needed right away) stayed in the terminal. A short status update for a team and a walk-through of eight steps still came back as text, once each.

**quickstart** returns everything for a new page in one result:

1. The page rules and how to work (`skills/artifact-design/contract.md`): what publishing wraps the file in, the title and icon, what loads, what a page opened from a `file://` link can't do, phones, light and dark, real content, and one look with `ArtifactCheck` before publishing. They are the plugin's own words, about a third the length of the contract they replace.
2. With a design system installed, what the system leaves to the model (`skills/artifact-design/craft.md`), then the system (see below). A design system gives a look and parts. It doesn't say whose look a page takes (the person's words, then their own product's or project's look, then the system), what the page is for and what it opens with, how the words read, when a numbered step or a label is true, what a diagram must show, or how to build a part the system lacks. Claude Code's skills said all of that along with the look, so a page built with a system used to get none of it. `craft.md` says it in the plugin's own words, short enough to send every time.
3. Where no system is installed, `design.md` instead. The two never come together: the general guidance warns against the very look a system may have. A page that leaves an installed system out, for a look the person named or their own product's, gets `design.md` from `guide` as the part `General design`.

`quickstart` takes no `intent` and ignores one passed out of habit.

**guide** returns parts of the installed design system by name: a section of its guide, another document, or a component with its doc and its worked example turned into page content, and the general design guidance by the name `General design`. `quickstart` carries the guide only as far as 22,000 characters, cut between sections, and lists the rest by name, so the whole result stays under 35,000 characters (about 34,500 with Sketchbook). Reading the same files from the plugin's folder would need a file read outside the project, which asks for permission in most modes.

**publish** takes one `.html` file. It wraps it in the skeleton, adds the design system to a page that asks for it, and writes it to `~/artifacts` (or `ARTIFACTS_DIR`), one folder per artifact with every version kept. The link is a `file://` page on this machine, so the result says which file to send to share it. Three things an earlier build did are gone:

- Markdown files rendered into Claude Code's plan template. A Markdown file is refused, and the rules say to build a page from its content.
- The bundled highlight.js runtime (600 KB in the plugin, inlined in any page with a tagged code block). A design system brings its own code blocks; without one, a page loads a highlighter from a CDN if it needs it.
- `edits` on a publish. A change is an edit to the file and a publish of the same path.

A page that was published before any of that reads back and republishes as before: old runtimes are taken out of it first.

**A design system** is a folder of plain files, laid out as a Design System artifact keeps them: `README.md` (the guide), other `.md` documents, `tokens.json` (or a ready `tokens.css`), `components/bundle.css`, `components/bundle.js`, a `README.md` and a `preview.html` per component, and the plugin's own addition, `checks/`. It is `ARTIFACT_DESIGN_SYSTEM` or the plugin's `design-system/`, and it is read fresh on every call. A page asks for it with one tag, `<meta name="design-system" content="<name>">`. A tag that is only written about, inside a comment, a script, a style or a textarea, asks for nothing. `publish` then adds the kit to that page: the tokens compiled to a stylesheet of variables (with a `prefers-color-scheme` block, since a page opened from disk has no `data-theme`, and without the class per type style that a Design System artifact also writes, since a bare `.number` or `.label` on every page would restyle the page's own classes), `bundle.css`, any libraries the system lists, and `bundle.js`, each escaped so that it can't end its own element. A page read back or published again has the kit taken out first, so the source file stays a few kilobytes of markup. A page that asks for no system is published as it is.

**Sketchbook** is the design system the plugin ships, in `design-system/`: the guide, the Drawing and Motion documents, the tokens, the stylesheet and runtime, and about eighty components with examples, twenty-five of them whole pages. It is Aaron's own system, drawn from Anthropic's public look. It leaves out three things the Design System artifact has that a page doesn't need: the cover card, the prompt for agents that can't load the system, and the notes for video.

**ArtifactCheck** renders the page as publishing wraps it, at desktop and phone widths in light and dark, and returns the captures with what breaks. Beyond the checks ported from Claude Code it has:

- The look (`scripts/look.mjs`): what a capture shows and no measurement of boxes finds. In each render: text too faint to read against what it sits on (WCAG's 4.5:1, or 3:1 for large text; text on a gradient that covers its box is read against the gradient's own colours and reported only when it is faint on every one; a switched-off control, text still fading in, text over a picture or over a gradient that draws only a line or a patch or fills the letters, and text hidden from a screen reader as decoration are left out), text that overlaps other text or lies under another element, a label in a drawing that a line runs through or that spills out of its shape, an id used twice, a font the page declares that did not load, and a 2D canvas with nothing drawn on it. A diagram the runtime drew from text is left out of the drawing, id and contrast findings, since the page can't change it, and so is text that is turned or pinned to the screen from the overlap findings. Then, in the first render, each control is pressed once (up to twelve, a few of each kind), and one that throws or hangs the page is reported. A control is reported as doing nothing only when two things hold: the page has set no handler that could hear it (none on the control, none around it for a press, a key, a hover or its form, and none for a press on the page as a whole, nor, for a link within the page, any watch on the address; the preview notes every listener as the page adds it), and pressing it sets off nothing the browser does by itself, such as a part that opens, a jump to a place on the page, a form put back or sent, or something the style sheet shows when the control takes the focus (a menu, a tip). A control inside a part with a shadow tree, or with something of its own group laid over it (a file field over a button), is not judged. So a control the page has wired is never called dead, whatever its handler does: a Pause that sets a flag, a button that stops a note, a library that hears every click at the root. That is on purpose, since a false alarm on a good page costs more than a missed fault, and it means a handler that is set and does nothing goes unreported, as does any dead control on a page that listens for clicks everywhere. A control with no handler is pressed a second time after the rest, with the page's empty fields filled in, since a form may wait for them. The press is the whole gesture, pointer down to click. A dialog, a new window, a download, the file picker, the clipboard and full screen are counted and not carried out, and whatever a press sets off is reported with the press, never as something the page did on load. A link to an id the page doesn't have is reported with that reason. A form a press sends is held back; one with no address to go to, which would reload the page, is reported as that, while one the page handles or sends somewhere is left alone, and so is a button that reloads the page or goes elsewhere (after a reload the pressing carries on with the controls that are left). It came from a build of the plugin that was never merged, where it also described a house look that is gone.
- `ARTIFACT_IMAGES=0` is for a session whose model can't see images. The result then carries no capture. Each render comes back in words instead: its size, its colours by area named after the page's own colour variables, its fonts by share of the text, and a map of its blocks as text. The tool's listing and `quickstart` say so.
- A label that a diagram holds as HTML inside a `<foreignObject>`, as Mermaid's are, and that is larger than the box the diagram gave it is reported as cut off.
- Four more general checks: running text that a grid or flex parent splits into separate rows or columns; an SVG whose labels draw too small to read at phone width; and an accent on one side of a box that bends round a rounded corner, as a coloured left border does on a card with rounded corners (a border on one side, an inset shadow pushed to one side, a thin bar at the edge of a box that clips it, a gradient with a hard stop). A full border, a tab's underline, a key cap, a meter's fill and a spinner pass. The fourth looks between the two widths a page is rendered at, where a layout can break in a window of widths only 30px across (a card whose content stops fitting just before its grid drops a column): the widest render is stepped down 8px at a time to the narrowest width, or to 320px when that is narrower, and whatever sticks out of its box sideways on the way is reported with the widths it was found at. The captures are taken first, so a pass between the widths that fails or runs out of time costs a note saying how far it got, never the captures.
- Scripts from the five CDNs the page rules allow load as they do on the published page, and one that fails or takes over 8 seconds is reported.
- For a page built with the design system: the kit is added; the capture is taken at rest (every part scrolled past once, a second with nothing moving, and the system's `checks/rest.js` satisfied), since a page that draws itself in would otherwise be captured half drawn; each other script in `checks/` runs after the capture and reports one line per fault (a script defines `check()`, and one that also defines `fits()`, which only measures, is asked at every third width in between too, 24px apart); and `checks/accept.json` names what the system does on purpose, which is then not reported: under `element_overflow`, the parts that reach past their box, and under `contrast`, the text it sets fainter than 4.5:1 with the ratio that text must still reach. A system's script is someone else's code: one that doesn't parse, throws, hangs, answers with something other than a list of lines or defines no `check()` costs a note, and it never runs a function of that name the page itself made. A page that asks for a system that isn't installed is previewed without one, and the result says so first, as publishing does.

Sketchbook's `accept.json` lists five kinds of text under `contrast`, each measured on its own examples: a button's white label on the clay fill (4.1:1), the mono label in accent on a putty or oat ground (3.9:1 at the least), a time stamp (4.4:1), a terminal's prompt sign and note lines (3.5:1), and the pill on a ticked task, which fades with its row (1.9:1). Making any of them reach 4.5:1 is a change to Sketchbook's colours.

Sketchbook's checks are `fit` (the words of a flow stay inside their step's card, an arrow's label stays clear of the steps, and no label runs out of the side of its drawing, at the widths shown and at every third width tried between them), `names` (every `sk-` class, `data-sk-` attribute and drawing name the page uses must exist: a name that is nearly right does nothing, without any error), `pen` (nothing hand-drawn is left undrawn or wiped on with a clip-path) and `page` (one theme from top to bottom, the page wrapper, two bands at most and never back to back, three hand marks at most, one boiling hero, no emoji).

The tool is listed only when a startup check finds Playwright and a Chromium, and `ARTIFACT_PREVIEW=0` turns it off. The listing takes the previous start's answer, kept in the temp folder, so that it doesn't wait for the check: Claude Code doesn't wait long for a plugin's server before the first turn. It finds Playwright beside the script or installed globally, never in the project, since the startup check would otherwise run the project's code.

**The artifacts folder.** Publishing a path again in the same session updates the same artifact; another session's publish makes a new one and names the earlier one, and `url` updates any artifact. A session outlives its server: a resumed one starts a new server, and Claude Code switches sessions under a running one without telling it. So each artifact lists the last eight Claude Code sessions that published it, from the `CLAUDE_CODE_SESSION_ID` Claude Code gives a server when it starts it, and a file in a drafts folder, which only the conversation that wrote it knows, counts as that conversation's; that also covers Codex, which passes no session ID. Publishing a page from inside the artifacts folder updates that artifact, a new artifact never takes a folder that is already on disk, and an unreadable `index.json` is set aside and rebuilt from the artifact folders.

**Drafts.** `quickstart` sends page files to a private drafts folder per session in the system temp directory, so they stay out of the project. Writes there get the usual permission check, which auto mode's reviewer passes.

**Inputs.** Paths must be absolute, because Codex starts the server in the plugin's folder. Links are accepted percent-encoded or not, as a folder or as its `index.html`. An unknown parameter is refused by name, with what to do here instead for the ones a model may pass out of habit (`edits`, `type_url`, `capabilities`, the asset-store ones). Codex passes a plugin's server only a fixed list of variables, so the manifest's `env_vars` names the server's own, Playwright's and the desktop ones a browser needs to open on Linux.
